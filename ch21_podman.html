第 21 章

部署方式二：Rootless Podman

為何需要本章

你沒有 Home Assistant，也不想為了一個服務去架 Kubernetes——這一章就是為這種情況存在的。一台 Linux、一個非 root 帳號、三個容器，交給 systemd 管理開機自啟與重啟。

它跟第 20 章那條路有一個關鍵差異：這個套件自帶一個常駐執行端。裝完之後主機清單不是空的，直接就有一台會幹活的機器，而且它掛的是跟其他 WoowTech 套件共用的那一份 pi 狀態。

本章會用到終端機。指令不多，但你需要能 ssh 進那台機器，並且那個帳號可以跑 systemctl --user。

三個容器各做一件事

容器映像角色
omnigent-postgrespostgres:16-alpine自己的資料庫，自己的磁碟區，完全不對外開埠
omnigent-server上游官方映像編排與網頁介面，只 publish 到 127.0.0.1:8000
omnigent-runner本套件自行建置常駐執行端，內含 pi 與共用磁碟區的包裝腳本，主動撥回伺服器

Quadlet：用一個 systemd 單元檔描述一個容器，交給使用者層級的 systemd 去啟動、重啟與排順序。相較於 compose 檔，它的好處是重開機後不需要任何額外的守護行程就會自己起來。需要 Podman 4.4 以上。

另外還有一個三十秒跑一次的健康檢查計時器，負責更新伺服器容器的健康狀態。三個容器共用一個私有的 Podman 橋接網路，資料庫只在這個網路內可見。

為什麼要一個常駐執行端

Omnigent 的伺服器只做編排與介面，代理實際上跑在另一個執行端行程裡，靠 WebSocket 撥回來。要補上這一塊有兩條路：讓每個人在自己的筆電上跑一個執行端，各自帶各自的 pi 狀態；或是在伺服器同一台機器上跑一個常駐執行端，掛共用的狀態磁碟區。這個套件選後者——網頁介面上開的任何 session 選了 pi，供應商與技能設定都已經是準備好的。

開始之前

  • Podman 4.4 以上，而且用非 root 帳號跑（rootless）
  • 那台機器連得到 GitHub 與容器登錄站，安裝過程要拉映像檔並在本地建置執行端映像
  • 強烈建議先裝姊妹套件 Woow_podman_pi_agent_package。它會建立共用的 pi 狀態磁碟區並把供應商與技能設定好；沒裝的話本套件會建一顆空的，你得從頭設一次供應商
  • 想過的話先想好對外要怎麼開。伺服器預設只綁在本機迴路位址上，不會自動對區域網路開放

安裝腳本裡的預設管理員憑證同時是執行端撥回登入用的憑證，也是人類管理員的帳號。它只有一份，改的時候兩邊會一起變——這是刻意設計，但也代表你不能只改一半。

安裝步驟

  1. 取得套件

    把 Woow_podman_omnigent_package 這個倉庫 clone 到那台機器上，切進目錄。裡面有 quadlet/（三個容器的單元檔）、systemd/（健康檢查計時器）、scripts/（安裝與移除）與 tests/（三支驗收腳本）。

  2. 先改掉預設密碼，再安裝

    執行端的單元檔裡有一組管理員帳密的預設值。在跑安裝腳本之前就改掉它，這樣第一次開機建立的管理員就是你自己的憑證，不必事後補救。另外一個選項是取消伺服器單元檔裡那行初始管理員密碼的註解，先把密碼種進去。

  3. 跑安裝腳本

    執行 ./scripts/install.sh。它會建置執行端映像、安裝所有單元檔，然後依 omnigent-postgres → omnigent-server → omnigent-runner 的順序啟動。已經建過映像、只想重裝單元檔的話，用 OD_SKIP_BUILD=1 ./scripts/install.sh 跳過建置。

  4. 等它自己把管理員建好

    腳本會一直等到伺服器的 /health 回傳 {"status":"ok"} 才收工，接著自動把管理員憑證送去建立第一個帳號。管理員已存在時它會收到重複的回應並靜默略過，所以重跑安裝是安全的。

  5. 跑三支驗收腳本

    tests/smoke-container.sh 驗三個容器都起來、伺服器健康、資料庫可連；tests/smoke-pi-integration.sh 驗 pi、包裝腳本、磁碟區與環境變數都對；tests/smoke-runner-dialin.sh 驗執行端連得到伺服器。三支全綠才算裝好。

  6. 開介面登入

    在那台機器上開 http://127.0.0.1:8000/，用你設的帳密登入。輸入區底部的主機選單裡應該已經有一台綠點主機，那就是常駐執行端。

資料放在哪，哪一份是共用的

磁碟區內容誰在用
omnigent-postgres-data資料庫，也就是 session、成本與帳號本套件獨佔
omnigent-server-data伺服器的工作檔案本套件獨佔
pi-agent-datapi 的供應商設定、技能與狀態四個套件共用：本套件、pi 網頁版、OpenDesign 版、code-server 版

共用那一份是整個設計的重點：你在 pi 網頁版設好的供應商，Omnigent 這邊開 session 選 pi 就直接能用，不必再設一次。做法是執行端容器用使用者命名空間對映（UserNS keep-id）把主機上的使用者身分和容器內對齊，共用磁碟區讀寫不需要改權限。

共用磁碟區的磁碟格式沒有版本化。升級本套件裡的 pi 版本時，必須同步升級姊妹套件的 pi 版本，否則兩邊會用不同版本去寫同一份狀態。這是這個設計唯一真正的代價。

移除時 ./scripts/uninstall.sh 只停掉並移除容器，保留本套件自己的兩個資料磁碟區；加上 --purge 才會一併刪除。共用的 pi 狀態磁碟區在任何情況下都不會被動，因為那是姊妹套件的。

對外連線怎麼處理

預設是保守的：伺服器只發布到 127.0.0.1:8000，資料庫完全不發布。也就是說裝完之後，只有那台機器上的人連得到。

要讓其他人連進來，套件建議的做法是走 Tailscale 的 HTTPS 服務，把本機迴路的 8000 埠掛到 tailnet 上的一個 HTTPS 埠：

tailscale serve --bg --https=9444 http://127.0.0.1:8000

這條指令要在跑 Tailscale 的容器裡執行。掛好之後用 https://<你的 tailnet 主機名>:9444/ 連線，憑證由 Tailscale 代為申請，瀏覽器不會跳自簽警告。

兩件事不要做。第一，不要把驗證關掉——那個開關存在是為了完全信任的封閉網段，一旦有對外通道就等於門戶大開。第二，注意首次開機的空窗期：管理員名單還空著的時候，建立第一個管理員的端點是不需要驗證的，誰先打到誰就是管理員。對策是照第 2 步先把密碼種好，或是開好之後立刻自己搶下來。

日常操作與升級

三個容器分開看日誌，問題通常一眼就分得出來是誰的。

  • podman ps 看三個容器的狀態，這是最快的一眼確認
  • podman logs -f omnigent-server 看介面與編排事件
  • podman logs -f omnigent-runner 看執行端的撥入與代理狀態
  • journalctl --user -u omnigent-server -f 看 systemd 這一層的啟停紀錄
  • systemctl --user restart omnigent-server 只重啟伺服器，不動資料庫與執行端

升級分兩邊。伺服器改單元檔裡的映像標籤（可以釘在特定版本），然後重啟該單元。執行端改建置檔裡的版本參數，重跑一次安裝腳本讓它重新建置，再重啟執行端單元。

怎麼確認做對了

  • 三支驗收腳本全綠。姊妹套件相關的那幾條在共用磁碟區是空的時候會跳過而不是失敗，這是預期行為
  • podman ps 三個容器都是執行中，伺服器那個顯示健康
  • 介面登得進去，主機選單裡的常駐執行端前面是綠點
  • 開一個 session 選 pi，真的收到回覆，而且不需要你重新設定供應商

絕對不要拿 /healthz 當健康檢查。介面是單頁應用，它的萬用路由會把 /healthz 變成回傳首頁並給你一個成功狀態碼——就算後端 API 已經死了，探針也會永遠是綠燈。要用的是 /health，它回的是真正的 JSON 狀態。

故障排除

  • 安裝腳本卡在等待伺服器健康：伺服器根本沒起來。開另一個終端機看 podman logs -f omnigent-server，常見原因是資料庫還沒準備好或映像拉取失敗。
  • 健康檢查一直綠燈，介面卻沒反應：你打的是 /healthz。改成 /health 再看一次，多半會發現後端其實是死的。
  • 執行端一直沒出現在主機選單：執行端登入失敗時會停在等待狀態不再重試，需要重啟 omnigent-runner 單元。第 22 章的 k3s 版用一個前置容器等到伺服器完成初始化才啟動執行端，就是為了避開這個情況。
  • 改了管理員密碼之後執行端掉線：那組憑證同時是執行端撥回登入用的。改密碼要連執行端單元檔一起改，然後重啟執行端。
  • 選了 pi 但沒有可用的供應商：共用磁碟區是空的。先裝姊妹的 pi 套件把供應商設好，或是進執行端容器手動設定一次。
  • 重裝之後舊資料不見了：你大概加了 --purge。不加的話移除腳本會保留資料磁碟區，重裝可以直接接上去。

常見問題

一定要先裝那個 pi 的姊妹套件嗎？

不是硬性的，但不裝的話共用磁碟區會是空的，你得自己進執行端容器把供應商與技能設一遍。先裝姊妹套件的好處是設定只做一次，pi 網頁版、OpenDesign、code-server 與這裡四個地方都吃同一份。

這個部署可以有幾個執行端？能不能加第二個？

套件設計是一個常駐執行端。你當然可以另外在別的機器上手動跑執行端撥進來，介面上會多出一台主機；但如果你的需求本來就是多台執行端各自獨立，第 22 章的 k3s 版是照這個需求設計的，每台主機一個部署、一顆自己的磁碟區。

我沒有 Tailscale，可以直接把 8000 埠開到區域網路嗎？

技術上可以，改單元檔的發布位址就行。但那等於把一個能在你機器上跑指令的服務暴露在區域網路上，而且是 HTTP 沒有加密。真的要這樣做，至少先確認驗證是開著的、密碼不是預設值，並且理解區域網路上的任何裝置都打得到它。

升級伺服器需要重新建置映像嗎？

不用。伺服器用的是上游官方映像，改單元檔裡的標籤再重啟就好。需要重新建置的是執行端，因為那個映像是本套件自己組的，pi 與 Omnigent 的版本寫在建置檔的參數裡。

為什麼健康檢查一定要打 /health 而不是 /healthz？

因為 /healthz 不是後端的端點。介面是單頁應用，任何沒被後端接走的路徑都會落到萬用路由，回傳首頁和一個成功狀態碼。用它當探針的結果是後端死了也永遠綠燈，你會完全看不到故障。/health 才是真的健康端點。
