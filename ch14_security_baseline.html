第 14 章

為何需要本章

附加元件的 Start 按下去、或者 Helm 安裝跑完，服務就通了。而它通的那一刻同時具備三個特徵：管理員密碼還是設定檔裡的預設值、伺服器的服務埠對整個區域網路開著、代理的行為規則一條都沒啟用。

這三件事單獨看都不致命，疊在一起就是最常見的破口：有人拿到網址、用預設密碼登進來、然後指揮一個能在你機器上跑指令的代理。

這一章是一份上線前的檢查清單。六個動作，全部在網頁介面或部署設定裡完成，不需要你懂容器或 Kubernetes。做完之後，這套系統才適合給你以外的人用。

如果這台 Omnigent 已經在被其他人使用了，先做「換密碼」跟「清點成員」這兩件，其餘的可以邊用邊補。順序不要顛倒。

三個暴露面

把「安全」拆成三個可以逐一檢查的面向，事情會好處理很多。

  • 帳號面：誰能登入這個網址。
  • 網路面：這個網址從哪些地方打得到。
  • 代理面：登入之後，代理被允許在你的機器上做什麼。

暴露面（attack surface）：一套系統對外可以被觸碰到的所有入口總和。縮小暴露面不等於把功能關掉，而是讓每一個入口都是你刻意留下的。

三者是乘法關係，不是加法。網路面收得再緊，只要帳號面是預設密碼，區網裡任何一台機器都能登進來；帳號面守得再好，代理面一條規則都沒開，一個講錯的需求還是可能刪掉東西。

第一次啟動的那個空窗

管理員名冊還是空的時候，建立管理員的 POST /auth/setup 端點不需要任何身分驗證——先打到那個網址的人就成為這台機器的管理員。

兩種部署都用「預先種好帳密」把這個空窗關掉：Home Assistant 附加元件在第一次開機時自動用設定分頁裡的帳密建立管理員；k3s 版由安裝後的 Job 打同一個端點。好處是沒有人搶得走，代價是你的預設密碼從服務起來的第一秒就是一組有效的登入密碼。這就是為什麼換密碼是第一件事，不是最後一件。

對外暴露了什麼

以 Home Assistant 附加元件版為例，它開的兩個埠角色完全不同。

埠用途誰應該碰得到
8000伺服器 API、執行端撥入、omnigent host 註冊區域網路上的執行端；需要跨網際網路時再經 Cloudflared 通道
8080網頁介面，經 nginx 轉給 Home Assistant 的 Ingress只有 Home Assistant 的 Supervisor，區網完全打不到
資料庫附加元件自帶的 Postgres只有附加元件本身，不對外發布

重點在前兩列的差別。你從 Home Assistant 側邊欄點進去看到的畫面走 8080，那條路只有 Supervisor 能走；但執行端要撥進來的是 8000，它必須在區網上開著，否則第 16 章的註冊會失敗。

想讓區網以外的機器也註冊進來，正規做法是搭配 Cloudflared 附加元件建一條通道路由到 8000，然後把附加元件設定裡的 base_url 改成那個公開網域。base_url 留空時系統會用區網位址，邀請連結也會跟著指到區網，外面的人點了打不開。

k3s 版的對外門面是 cloudflared，公開網址就是你在 chart 裡設定的那一個。通道憑證放在叢集的一個 Secret 裡，那份 JSON 永遠不要進版本控制。

開始之前

動手前先備齊三樣東西：

  • 一個 Admin 角色的帳號（角色寫在 Settings 的 Members 頁）
  • 部署設定的存取權——附加元件版是 Home Assistant 的 Configuration 分頁，k3s 版是 Helm 的 values
  • 一份「誰應該有帳號」的名單，寫在紙上也行

改部署設定要重啟才生效。附加元件版改完 Configuration 要重新啟動附加元件；k3s 版要跑一次 upgrade。改完沒重啟，舊密碼還活著，而你會以為自己已經換掉了。

上線前的六個動作

  1. 換掉安裝預設的管理員密碼

    附加元件版在 Configuration 分頁有 admin_username 與 admin_password 兩個欄位，官方文件在密碼那一列直接標了「Change me」。把它改成你自己的 <your-password>，儲存，重新啟動附加元件。

    k3s 版的預設帳密寫在 chart 的 values.yaml 裡，用安裝參數覆寫，或者放進一份不進版本控制的私有 values 檔。無論哪一種，改完之後不要把新密碼寫回會被推上去的檔案。

  2. 清點 Members 名單

    到 Settings 的 Members 頁。表格有四欄：USERNAME、ROLE、LAST LOGIN、ACTIONS。角色只有 Admin 與 Member 兩種。

    逐行問自己兩個問題：這個帳號我認得嗎？它需要 Admin 嗎？認不得的用 ACTIONS 欄的 Remove 移除；認得但權限過高的，先用 Reset 重設密碼再談降權。日常使用者給 Member 就夠，第 11 章講得更細。

  3. 決定 Session sharing 停在哪一段

    Settings 的 Sharing 頁把分享分成四段，由寬到窄是 On、Read only、Read only (restricted)、Off。多數團隊適合停在 Read only：新的分享上限是唯讀，要求 edit 或 manage 的分享會被拒絕。

    Read only (restricted) 多一層保護——工作目錄是家目錄或檔案系統根的 session 完全不可分享。如果你的成員習慣直接在家目錄開 session，這一段值得考慮。

  4. 決定 8000 要不要出區網

    只在自家網路內用，就讓它留在區網，不要另外開通道。需要遠端註冊執行端或遠端登入，才建 Cloudflared 通道，並且同時把 base_url 設成公開網域。

    兩者要一起做。只開通道不改 base_url，邀請連結還是會指回區網位址；只改 base_url 沒開通道，外面根本連不上。

  5. 至少啟用一條 Policy

    Settings 的 Policies 頁預設是空的，畫面上寫著沒有設定任何全域規則。內建目錄有二十五條可選，第一次只要挑一條開始。

    三個好起點：Session Cost Budget（單一 session 的累計花費到頂就擋）、Block Dangerous Shell Commands（安全指令放行，高風險指令改成詢問或直接拒絕）、Require Approval for File & Shell Operations（任何檔案或 shell 動作前先問你）。挑法與副作用見第 12 章。

  6. 把金鑰放在該放的地方

    附加元件設定裡的 env_vars 可以塞任意環境變數，常見用途是放模型供應商的 API 金鑰。這些值只有伺服器行程看得到；執行端自己帶自己的憑證，不會從這裡拿。

    所以不要為了「讓代理能用」而把個人金鑰重複貼到兩邊。哪一邊需要，就只放在那一邊。

分享設定有一個反直覺的地方

Sharing 頁除了四段式的 Session sharing，還有一個獨立的 Public access 開關，管的是「能不能用一條連結公開唯讀分享」。

把它關掉之後會發生三件事：Share 對話框裡的 Public access 切換會消失、新的公開分享會被拒絕——然後是第三件，也是最容易誤會的那件：已經公開出去的 session 在你逐一撤銷之前，仍然是公開的。

設定頁的原文寫得很直白：變更只影響新的分享，既有的授權（包含已經公開的 session）在被撤銷之前都繼續有效。關掉開關不等於把流出去的連結收回來。

所以「收回公開連結」是兩個動作，不是一個：先關掉 Public access 擋住未來，再回到每一個已經分享出去的 session 逐個撤銷。第 9 章講分享對話框的操作，這裡只提醒順序。

怎麼確認做對了

五個檢查，全部從瀏覽器就能做完。

  • 登出，用安裝預設的帳密登入——應該失敗。成功的話代表設定沒生效，多半是漏了重啟。
  • Settings 的 Members 頁每一行都認得，而且 Admin 的數量等於你預期的數量。
  • Settings 的 Sharing 頁停在你選的那一段，Public access 的狀態也是你要的。
  • Settings 的 Policies 頁不再顯示「沒有設定任何全域規則」，至少列著一條。
  • 從一台不在你家網路上的裝置打這個網址，結果符合你的預期——該連不上的連不上，該連得上的登入畫面正常。

故障排除

  • 徵狀：改了密碼，舊密碼還是登得進去。設定沒重新載入。附加元件版要重新啟動附加元件，k3s 版要跑 upgrade。另一種可能是你改了設定卻沒儲存就切換分頁。
  • 徵狀：關掉 Public access 之後，之前分享的公開連結還打得開。這是設計行為，不是故障。開關只擋新的分享，既有授權要逐一撤銷。
  • 徵狀：Members 頁出現不認識的帳號。最可能是第一次啟動的空窗被別人搶先，或有人拿預設密碼登入後自行建立帳號。先把它移除，再換掉管理員密碼，然後檢查 Sharing 有沒有被人放寬。
  • 徵狀：網頁開得起來，但一直停在登入表單。自動建立管理員用的是部署設定裡的那組帳密。回去對一次 admin_username 與 admin_password，你手上的密碼跟設定裡的可能不是同一組。
  • 徵狀：外部同事打不開你給的連結。通道與 base_url 沒有成對設定。先確認通道確實路由到 8000，再確認 base_url 填的是公開網域而不是區網位址。
  • 徵狀：啟用了 Policy，代理行為卻沒變。Policies 頁管的是全域規則，加完要確認它真的列在清單上；若清單是空的，代表新增沒有存進去。第 12 章有逐條的判讀方式。

常見問題

這一章的內容適用於哪些部署方式？

網頁介面裡的三個動作——清點 Members、調整 Sharing、啟用 Policy——三種部署方式都一樣，因為那是同一套伺服器的設定頁。換密碼與埠的部分則依部署方式而異：附加元件版在 Configuration 分頁，k3s 版在 Helm 的 values，Rootless Podman 版的做法見第 21 章。

我只是自己一個人在家裡用，這些還要做嗎？

換密碼要做，其餘可以簡化。理由是代理面：就算沒有別人登入，一個誤解需求的代理仍然能在你的機器上跑指令。所以即使單人使用，也建議至少開一條規則——成本上限或危險指令攔截，兩者擇一。

做完這一章之後我應該看到什麼？

登入畫面拒絕安裝預設密碼、Members 頁沒有陌生帳號、Sharing 停在你選的那一段、Policies 頁至少列著一條規則。這四件事是這一章的全部成果，其他章節的操作都建立在它們之上。

把 8000 關掉是不是更安全？

更安全，但也更沒用。8000 是執行端撥進來的那個入口，關掉之後就沒有任何機器能註冊，主機清單會一直是空的，你只剩一個沒有工人的指揮台。正確的做法不是關掉它，而是決定它開放給哪個網段，以及要不要再經過一條通道往外開。

如果畫面跟書上不一樣，是版本差異還是我做錯了？

先看「固定來源」指向的 commit——本章的欄位名稱與預設值都以那兩個 commit 為準。三種部署方式的版本本來就有落差，設定欄位可能多一兩個或改過名字。但 Settings 底下的 Members、Sharing、Policies 三頁是伺服器共通的，如果連這三頁都對不上，比較可能是你登入的角色不是 Admin，管理類分頁不會顯示給一般成員。
