Appendix A

附錄 A：三種部署的安裝速查表

這份速查怎麼用

第 19 到 22 章把三種部署方式各講了一遍，包含為什麼那樣設計、每個選項的意義、以及裝完之後要怎麼運維。這份附錄不重複那些，它只做一件事：把你真正要打的指令、要點的按鈕、要等的訊號，壓成可以邊看邊做的表。

建議的用法是：第一次安裝先讀正文那一章，第二次以後直接看這裡。表格裡每一列都會標出對應章次，忘記為什麼要這樣做的時候翻回去。

這份附錄不是正文的替代品。三條路線都不是一鍵完成，每一條都有一個「裝完但還不能用」的中間狀態——最常見的就是伺服器起來了、介面登得進去，但主機清單是空的。看到那個畫面不代表你裝錯了，代表你還差最後一步。

三條路線的共同骨架

不管你選哪一條，裝起來的東西都是同一組零件：一個 Postgres 資料庫、一個 Omnigent Server（含網頁介面與 API），以及一個或多個 Runner（在被指揮的機器上常駐、把工作真正做掉的那個行程）。

三條路線的差別只有兩個：誰負責把這些零件叫起來，以及 Runner 從哪裡來。把這兩件事記住，下面的表就不需要背。

附加元件（add-on）：Home Assistant 的擴充套件形式，由 Supervisor 負責安裝、啟動與備份。
Quadlet：Podman 用來把容器描述成 systemd 單元的設定格式，讓容器像系統服務一樣被管理。
Helm chart：Kubernetes 的套件格式，一份 chart 描述一整組要一起部署的資源。

版本方面，三個套件目前存在已知的落差，這件事本身被記在 source-lock.json 的 versionDriftKnown 欄位裡，不是筆誤。

部署方式套件版本該 commit 所載的 Omnigent 核心正文章次

開始之前：五件先決定好的事

這五件事三條路線都會問你，臨時想會拖慢整個安裝。

  • Server 要放哪台機器：它要長時間開著，而且 Runner 要連得到它。
  • 第一個管理員帳密：三個套件都帶了預設值，而且都寫在設定檔裡。安裝當下就換掉，不要留到「之後再說」。本書不列出任何一組實際值。
  • 對外通道要不要開：只在區網用就不用開。要從外面連，Podman 版走 Tailscale、k3s 版走 cloudflared、Home Assistant 版可以搭 Cloudflared 附加元件。
  • Runner 要跑在哪：這決定代理實際能碰到哪些檔案。Home Assistant 版一定要另外接一台，理由見第 15 章。
  • 資料怎麼備份：Postgres 裡有全部的 session、成本紀錄與管理員資料。三條路線的備份機制不一樣，見下面的驗證表。

五步通用流程

不管走哪一條，順序都是這五步。每一步下面按路線分列。

  1. 選定路線

    照上面的對照表挑一條。判斷不出來就用這個順序：家裡已經有 Home Assistant 就選附加元件；有一台常開的 Linux 機器就選 Podman；已經在跑 k3s 才選 Helm。三條可以並存，但沒有必要——它們是三套獨立的資料庫，session 不互通。

  2. 把套件裝上去

    Home Assistant：Supervisor → Add-on Store → 右上三點 → Repositories → 貼上附加元件倉庫網址 → 安裝 Woow Omnigent → 在 Configuration 分頁改掉預設帳密 → Start。首次開機要等大約 30 到 60 秒，Postgres 要先初始化。

    Podman：git clone 套件倉庫後進入目錄，執行 ./scripts/install.sh。它會依序把 omnigent-postgres、omnigent-server、omnigent-runner 叫起來。不想重建 runner 映像檔時加 OD_SKIP_BUILD=1。

    k3s：先備妥 cloudflared 通道憑證的 JSON 檔，再執行 CF_CREDS_JSON=/path/to/creds.json scripts/apply.sh install（需要指定叢集時另外帶 KUBECONTEXT）。不想 clone 倉庫的話，chart 也發佈成 OCI 產物，可以直接 helm install omnigent oci://ghcr.io/woowtech/charts/omnigent --version 0.1.0 --create-namespace -n omnigent --set-file cloudflared.credentials=creds.json。

  3. 等伺服器回應健康檢查

    三條路線的安裝腳本都會等 /health 回 {"status":"ok"} 才算完成。不要改用 /healthz：那個路徑會被前端的萬用路由接走，就算 API 已經死了也回 200，健康檢查永遠不會失敗。這是套件文件裡特別標紅的一條。

  4. 換掉預設管理員憑證並登入

    三個套件都會在第一次開機時自動宣告管理員（POST /auth/setup），值取自設定檔。在把服務給任何其他人看到之前先換掉。Home Assistant 版改 Configuration 分頁的 admin_username 與 admin_password；Podman 版改 Quadlet 單元裡的環境變數；k3s 版用 --set admin.username=…、--set admin.password=… 或一份私有的 values 檔覆寫。

  5. 接上第一台 Runner

    Podman 與 k3s 版自帶 Runner，這一步可以跳過。Home Assistant 版一定要做，因為附加元件只包伺服器。在任何一台同區網的機器上安裝 pi 與 omnigent 命令列工具（npm install -g @earendil-works/pi-coding-agent@0.85.1 與 pip install omnigent==0.12.0），然後執行 omnigent host --server http://homeassistant.local:8000 註冊。詳細步驟與版本對應在第 16 章。

綠點出現、但你送出的第一句話沒有回應，先不要重裝。那是 Runner 端的問題，附錄 B 有對應的徵狀列，第 18 章有完整的診斷流程。

裝完立刻做的四件事

這四件事在正文第 14 章有完整說明，這裡只列動作。

  • 換掉預設管理員帳密：三個套件的預設值都寫在公開倉庫的設定檔裡，任何人都查得到。這是四件事裡唯一不能延後的。
  • 確認 Postgres 沒有對外：三條路線的預設都是不對外發佈資料庫連接埠，升級或改設定時不要不小心打開。
  • 不要關掉內建帳號驗證：Podman 套件用 OMNIGENT_AUTH_ENABLED 控制，關掉之後任何連得到網址的人都是管理員。只有在完全信任的網段內才考慮，而且沒什麼理由這樣做。
  • 處理第一次開機的空窗：管理員名冊還是空的時候，宣告管理員的那個端點不需要驗證——先開到網址的人就拿走整台機器。做法是安裝前先在設定檔預先填好密碼，或者裝完自己第一個開。

還有第五件事值得馬上做，但它不在安裝腳本裡：去 Settings → Policies 開規則。內建目錄有 25 條，預設一條都沒啟用，新裝好的站台在 Global Policies 會顯示沒有設定任何全域規則。細節見第 12 章。

安裝期故障排除

這裡只收安裝當下會遇到的。裝完之後的日常故障在附錄 B。

  • 介面開得起來，但一直停在登入表單：自動宣告管理員成功了，是你用的密碼不對。回設定檔看 admin_username 與 admin_password 實際被設成什麼，不要憑印象輸入。
  • 登入之後主機清單是空的：Home Assistant 版的預期行為，附加元件不包 Runner。回到第五步接一台上去。Podman 與 k3s 版出現這個狀況才是異常，先看 runner 容器的記錄。
  • 宣告管理員的請求回 500：幾乎都是 Postgres 沒起來。看記錄最前面有沒有初始化資料庫的錯誤，那段每次開機都會印在最上面。
  • Runner 註冊成功了，但對話沒反應：pi 的擴充套件衝突。清掉 Runner 那台機器上 pi 的外掛目錄，並把衝突的登入設定從 pi 的驗證檔裡移除，然後重新連線。
  • 健康檢查一直是綠的，但 API 其實是死的：你把探針指到 /healthz 了。前端的萬用路由會對那個路徑回 200，換回 /health。
  • k3s：Postgres 重啟之後伺服器很久才恢復：chart 內建 pgbouncer sidecar 就是為了這件事。確認它沒有被關掉；連線池模式必須維持在 session，換成其他模式會打壞伺服器用的預備語句。

常見問題

我可以先把伺服器裝起來，過幾天再接 Runner 嗎？

可以。Home Assistant 版本來就是這樣設計的——附加元件只包伺服器，主機清單空著是正常狀態。你可以先登入把介面摸熟、把成員邀好、把規則設好，等要真的派工的時候再接機器。Podman 與 k3s 版自帶 Runner，反而沒有這個選擇。

三種部署可以同時裝嗎？

技術上可以，它們互相不知道對方存在。但實務上沒什麼理由這樣做：每一套有自己的 Postgres，session、成本紀錄、成員名單、規則設定全部各自獨立，不會同步。你只會得到三個要各自維護、各自備份的站台。要換路線的做法是重裝，不是並存。

為什麼 Podman 版用 Tailscale，k3s 版用 cloudflared？

因為兩者的對外情境不同。Podman 版預設只把伺服器綁在本機迴路上，對外那道門交給 Tailscale，適合「只有我和我的裝置要連」。k3s 版預設要一個公開網址，所以用 cloudflared 打通道。兩者都不是硬性規定，只是套件預設；Home Assistant 版則可以搭 Cloudflared 附加元件走同樣的通道模式。

套件版本跟這裡寫的不一樣，要更新嗎？

不一定。三個套件各自跟著上游走，版本落差是已知且被記錄下來的狀態，不是壞掉。判斷標準是「功能對不對得上」而不是「數字一不一樣」：介面上找不到書裡提到的東西，才需要看是不是版本太舊。真的要更新，看該套件倉庫的升級說明，不要直接把映像檔標籤改掉。

一定要用 pi 這個代理嗎？

不用。pi 只是三個套件預設先接好的那一個，因為 Runner 映像檔裡已經裝好它。介面上的代理清單有十一種框架與四個內建代理，沒設定過的會標上 needs setup。你完全可以只用 Claude Code 或 Codex，把其他的藏起來——外觀設定裡有一個開關可以隱藏未設定的項目。第 17 章比較各家的取捨。
