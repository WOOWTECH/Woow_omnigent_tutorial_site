第 18 章

Runner 疑難排解：離線、孤兒與無回應

為何需要本章

Host picker 上那個綠點很好認，也很容易被過度解讀。它只說明一件事：Omnigent 這一側收得到那台主機的訊號。它不保證你選的框架已經登入、不保證排程開火的那一刻機器還醒著、更不保證你會拿到一段有內容的回覆。

這一章把「代理沒動」拆成可以逐層排除的幾種情況，並且給每一種一個明確的下一步。綠點不代表真的能用，是這章從頭到尾的主軸。

本章的多數處置，最後一步都落在那台機器上，不在瀏覽器裡。如果那台機器不是你的（同事的筆電、機房裡的伺服器），你能做的是把問題辨識清楚，然後交給管得到它的人——這件事本身就很有價值，因為多數往返都浪費在講不清楚徵狀。

三層要分開看

從你按下送出到拿到回覆，中間至少疊了三層，而且它們是各自獨立的。

執行端（runner）：真正在機器上把代理跑起來的那一端。Omnigent 的網頁只負責派工與顯示，動手的是它。

層在問什麼介面上的指示燈
第一層　主機連線那台機器現在連得上嗎Host picker 名稱前的綠點；Import sessions 頁的 ONLINE 徽章
第二層　框架可用性那台機器上有把這個框架設好嗎Runs with 下拉的 needs setup 徽章
第三層　框架的帳號認證那個框架自己的登入還有效嗎沒有。事實庫沒有記錄任何顯示框架登入狀態的畫面

第三層沒有指示燈，這是本章存在的主要理由。綠點亮著、框架也沒標 needs setup，仍然可能因為第三層而拿不到回覆，而且畫面上不會有任何一行字告訴你是這個原因。你只能從徵狀反推。

徵狀對照表

先用這張表把問題丟到正確的那一層，再往下做。省下來的時間比想像中多。

開始之前先蒐集三件事

動手之前，把這三件事寫在便條紙上。沒有它們，你會在同一個畫面上來回猜。

  • 哪一台主機：抄下 Host picker 顯示的完整名稱，包含括號裡的那一段，例如 Pi Web ChatGPT (pi5)。名稱相近的多台是誤判的主要來源。
  • 哪一個框架：Runs with 選到的那一個。換框架之後徵狀會變，不記下來就對不起來。
  • 最後一次好過是什麼時候：昨天還能用，跟從來沒用過，要查的方向完全不同。

還有一件要先想清楚的事：你碰得到那台機器嗎？本章一半以上的修法要在機器上執行，不是在網頁裡點。碰不到就先把辨識做完，再找人。

分階段診斷

照順序做，不要跳。每一步都是在排除一整層，跳過就等於把可能性留著。

  1. 確認你看的是同一台主機

    Composer 底部第一個 picker 就是 Host。把它展開，確認選中的名稱跟你便條紙上那一行完全一樣，而且前面有綠點。先排除選錯機器，這是最常見也最尷尬的原因。

  2. 用 Import sessions 交叉驗證第一層

    到 Settings 的 Import sessions 分頁。那裡的 Machine 欄會列出同一批機器，線上的會帶一個 ONLINE 徽章。兩個畫面都說線上，第一層就可以劃掉了。

  3. 排除第二層

    回 Composer 打開 Runs with，看你要用的那個框架有沒有橘色的 needs setup。有的話問題就在這裡，往第 17 章走，本章後面的內容都用不上。

  4. 用一句最小的話測第三層

    開一個新 session，只送一句最短的指令，例如請它回覆兩個字。有內容的回覆代表三層都通；如果是空白、或幾乎沒等就結束，指向第三層的帳號認證。

  5. 用 Usage 反查它曾經跑起來過

    到 Usage 把期間切到 30 days，看 Cost by harness。那個框架有花費，就代表它在這段期間真的跑起來過，問題是「後來壞了」而不是「從來沒通」。這兩件事的查法不一樣。

  6. 最後才去動那台機器

    確定問題在第三層之後，處置只有一種：在那台機器上把該框架重新登入一次。這件事必須有人實際操作那台機器，網頁裡沒有可以續期的地方。第一層沒過的話，則是回第 16 章重跑註冊。

怎麼確認真的修好了

五個條件同時成立，才算修好，少一個都可能是錯覺：

  • Host picker 裡對應這台機器只有一筆，而且有綠點
  • Import sessions 的 Machine 欄顯示 ONLINE
  • Runs with 裡你要用的那個框架沒有 needs setup
  • 最小測試句在同一個 session 內拿到非空回覆
  • 隔天到 Usage 把期間切到 7 days，看得到這次產生的花費

早期一份端對端測試報告的結尾寫著某個框架「依然不會回覆」。2026-09-09 的實機記錄已經推翻它：Usage 顯示三十天內有二十個 session 與累計成本，主機也顯示綠點。碰到疑似「這個框架根本不會回」的時候，先照上面五點跑一遍，不要直接下結論——把問題歸給產品，往往只是漏掉了第三層。

孤兒主機：清單裡那筆永遠不會亮的

機器重開、或註冊流程被跑了第二次之後，清單裡可能留下一筆再也不會亮綠點的舊項目。它的名稱有時跟現役那一台一模一樣，這是它麻煩的地方。

  • 怎麼辨識：綠點是唯一可靠的判準，名稱不是。兩筆同名就挑亮的那一筆。
  • 為什麼危險：在 Composer 選到孤兒，送出去會沒有反應；更麻煩的是 Automations 的 Host 欄如果指定到孤兒，任務到點開火時打不到任何人，而且不會有人在旁邊發現。
  • 怎麼避免：Automations 的 Host (optional) 欄留在預設值 Resolve at fire time。官方說明是 Leave unset to run on your connected host when the task fires.——不綁死，就不會綁到孤兒。
  • 怎麼清掉：事實庫沒有記錄刪除主機的介面，所以本書不寫步驟。真的要清，得由管得到那套部署的人處理。在那之前，靠綠點辨識就足以正常使用。

排程到點卻什麼都沒發生

Automations 頁自己那句說明就是線索：Run agent sessions on a recurring schedule. Tasks fire on a connected host.關鍵字是 connected——排程需要開火那一刻有一台線上的主機，不是設定當下有就好。

依序檢查三件事，多數情況在第一或第二項就找到了：

  1. 它是不是被暫停了：Automations 清單頁上方有 All、Active、Paused 三個篩選頁籤。切到 Paused 看看你要找的那條在不在裡面。
  2. 開火時有沒有線上主機：如果 Host 綁死到某一台，那台在半夜是關機的，任務就落空。改回 Resolve at fire time 通常就解決了。
  3. Permission mode 是不是會停下來問：對話框裡寫得很直白，a prompting mode (Manual or Plan) will wait for approval that never comes。無人值守的排程配上會提示的模式，等於永遠卡住。

排程失敗最麻煩的地方是它是安靜的。沒有人在旁邊，也不會有紅字跳出來。如果某件事重要到要排程，就要有人定期回頭看 Usage 與 Inbox 確認它真的跑過。

故障排除

  • 主機有綠點，但送出去完全沒反應：綠點只覆蓋第一層。往下查第二層的 needs setup，再用最小測試句判斷第三層。三層都通還是沒反應，記下時間與主機名稱再找人。
  • 回覆是空的，或一送出就結束：最可能是那個框架的帳號認證過期。這件事必須有人在那台機器上重新登入該工具；Omnigent 網頁裡沒有可以續期的地方，等再久也不會自己好。
  • 清單裡有兩台名字一樣的主機：選有綠點的那一筆，另一筆是孤兒。順手把 Automations 的 Host 欄改回 Resolve at fire time，免得排程綁到死的那一筆。
  • 排程到點沒跑：依序看三件事——清單頁籤是不是停在 Paused、Host 欄是不是綁到不在線的主機、Permission mode 是不是 Manual 或 Plan。
  • 不確定代理是不是在等你回答：看 Inbox。沒東西時它會寫 Nothing waiting on you，那代表確實沒有人在等你，而不是通知掉了。
  • 換一台主機之後一切正常：那就確定問題在原本那台機器上，不在 Omnigent。把主機名稱、框架名稱與時間交給管那台機器的人，比反覆重試有用。

常見問題

綠點是即時更新的嗎？

事實庫只記錄了它代表線上，沒有記錄更新頻率，所以本書不給秒數。要交叉驗證就用 Import sessions 的 ONLINE 徽章：兩個畫面都說線上，可信度比盯著一個點高。

我可以在網頁裡把一台不用的主機刪掉嗎？

本站的實機記錄裡沒有刪除主機的畫面，所以本書不寫步驟，也不建議你亂試。孤兒主機不會主動害你，只要記得靠綠點而不是靠名稱挑，就能正常使用。真的要清理，交給管那套部署的人。

認證過期為什麼不能由 Omnigent 自動處理？

因為那些帳號屬於各個框架，登入動作發生在主機上，不在 Omnigent 這一側。它派得動工具，但不保管工具的登入。這也是為什麼第三層沒有指示燈——它看不到那一層。

我怎麼知道問題出在 Omnigent 還是那台機器？

用三層法。第一層有問題（沒有綠點、清單裡沒有那台機器），問題在機器或網路。第二、三層有問題，問題在那台機器上的框架設定或登入。三層都通卻還是沒回覆，那才輪到懷疑服務本身，而且那時你手上已經有一組清楚的徵狀可以交出去。

之前有人說某個框架根本不會回覆，是真的嗎？

那個說法已經被推翻。2026-09-09 的實機記錄顯示，Usage 有三十天二十個 session 的用量與累計成本，主機也是綠點。當時看到的很可能是第二層或第三層的問題被誤讀成產品缺陷。這正是本章要你先跑完五點檢查再下結論的原因。
